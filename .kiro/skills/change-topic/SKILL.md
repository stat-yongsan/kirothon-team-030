# 주제 변경 절차

**입력:** `challenge.md`(문제 원문 + 이번 MVP 항목), 현재 코드와 활성 Spec.
**출력:** 갱신된 `.kiro/specs/mvp/*`, `src/domain/<새 주제>.ts`, `src/domain/fixtures/<새 주제>.ts`, 관련 테스트, `src/domain/current.ts`, `docs/DEMO.md`, 변경 요약.
**종료 조건:** `node scripts/quality.mjs task` PASS + 정상 샘플로 초안·검토·다운로드를 실제 화면에서 1회 확인. 실패하면 원인과 남은 작업을 보고하고 멈춘다.

## 단계

1. **원문 추출** — `challenge.md` 원문에서 대상 사용자, 핵심 불편, 제공 데이터(형식·열), 제출 조건·심사 기준을 뽑아 "이번 MVP" 항목을 갱신하고 "변경 메모"에 날짜와 요약을 남긴다. 원문은 고치지 않는다.
2. **범위 자르기** — 가장 짧은 시연 경로(입력 → 코드 판정 → Claude 설명 → 사람 검토 → 내보내기)를 고르고 기능을 3개 이하로 제한한다. 이 앱 구조(문서·데이터 입력 → 분석·분류·추천 → 사람 검토)에 맞지 않으면 그 사실과 대안을 먼저 보고한다.
3. **Spec 일괄 갱신** — requirements(인수 조건은 검증 가능한 수치·상태로)/design/tasks(6~8개, 각 작업에 검증 명령)를 한 번에 다시 쓴다. 기존 `[x]`를 새 주제의 완료로 재사용하지 않는다. 미확정 사항은 가정 목록에 적는다.
4. **도메인 교체** — `src/domain/types.ts`의 `DomainAdapter`를 구현하는 새 어댑터를 만든다. CSV면 `parseCsv`를 재사용한다. 계산·판정은 코드에, 근거(evidence)에는 ID·값·출처를 넣는다. fixtures에 정상·오류·경계값을 손 검산 주석과 함께 두고 `samples`에 연결한다(정상·오류 샘플은 API 경계 테스트가 자동으로 사용하므로 필수). `current.ts` 한 줄을 바꾼다. 기존 예제 파일은 지우지 않는다.
5. **테스트** — 새 어댑터 테스트를 손 검산 상수로 작성한다(정상 수치, 오류 행 번호, 0·경계값). 구현 로직을 테스트에 복사하지 않는다.
6. **AI 출력 구조 확인** — 기본 구조(summary/sections+evidenceIds/cautions)로 충분하면 공통 엔진을 유지한다. 바뀌어야 하면 `src/lib/ai/schema.ts`, 서버 검증, `DraftPanel`, `markdown.ts`를 함께 고치고 테스트를 맞춘다.
7. **화면·대본** — 어댑터 문구(title, tagline, user, input, samples)와 `docs/DEMO.md` 3분 대본을 새 주제로 바꾼다. `challenge.md`의 "대표 성공 장면"과 "출력"이 화면에 그 모습 그대로 보이게 한다(예: "카드 3장"이면 표가 아니라 카드 UI). 공통 레이아웃·오류 UI·내보내기는 유지한다.
8. **검증·보고** — `node scripts/quality.mjs task` → 화면에서 오류 샘플·정상 샘플·대표 성공 장면·초안·검토·다운로드 확인(verify-mvp 스킬). 바뀐 파일 목록, 실행한 명령과 결과, 대표 성공 장면 충족 여부, 남은 가정을 보고한다.

파일 저장만으로 모델이 자동 실행되지 않는다. 사용자가 "주제 변경 적용"을 요청할 때 이 절차를 실행한다.
